# a800: полный RAGU одновременно для двух Meno, без судьи

Скрипт [meno_pair_a800.sbatch](scripts/meno_pair_a800.sbatch) запускает **только Meno-Lite-0.1 и Meno-Lite-0.2**, по **1543 вопроса** русского RUMBA `test`: память → поиск → ответы. Qwen и Pollux в задании отсутствуют. Основной процесс — [run_meno_pair.py](scripts/run_meno_pair.py).

Этот профиль использует шесть GPU A100/A800 по 80 GB на одном exclusive-узле с 32 CPU. При проверке фактического узла обнаружены десять A800 80 GB и драйвер 560.35.05. В целевой очереди `a800` GPU GRES не настроен: шаблон запрашивает целиком один узел через `--exclusive`, без `--gres`. Если `CUDA_VISIBLE_DEVICES` назначен Slurm, используются только эти устройства. Если переменной нет, скрипт проверяет exclusive-выделение одного узла через `scontrol`, прежде чем выбирать локальные GPU. Запуск на login node запрещён.

## Подготовка

Нужны `.venv-ragu` из `requirements-ragu.lock`, отдельный `.venv-vllm` с vLLM 0.29.0, подготовленные `data/` и полный BM25-кэш `.cache/fastembed/`. См. [общий runbook](README_A100_CLUSTER.md). На compute node доступ к интернету не нужен. В `runs/cluster-setup/bootstrap.status` должно быть `ready`; шаблон допускает ожидание фоновой подготовки на headnode до часа и сразу останавливается при `failed:*`.

Для драйвера 560 выбран официальный CUDA-12.9 wheel vLLM вместо PyPI-сборки с CUDA 13; PyTorch берётся из соответствующего cu129 index. Установка выполняется в отдельном окружении, без изменения драйвера узла:

```bash
.venv-vllm/bin/python -m pip install \
  --extra-index-url https://download.pytorch.org/whl/cu129 \
  'vllm @ https://github.com/vllm-project/vllm/releases/download/v0.29.0/vllm-0.29.0%2Bcu129-cp38-abi3-manylinux_2_28_x86_64.whl'
```

Источник binary: [официальный релиз vLLM 0.29.0](https://github.com/vllm-project/vllm/releases/tag/v0.29.0). Фактическую CUDA-совместимость и запуск kernel нужно проверить в allocation. При долгой подготовке задание можно держать в `requeuehold` и освободить после offline-validation: занимать GPU ожиданием скачивания не требуется.

Если подготовка сделана вручную по общей инструкции, после проверки установки обоих окружений, четырёх моделей, полного датасета и offline BM25 создайте индикатор готовности: `mkdir -p runs/cluster-setup; printf 'ready\n' > runs/cluster-setup/bootstrap.status`. Сам индикатор не скачивает отсутствующие ресурсы; реальные проверки выполняются перед стартом.

Веса берутся из `MODELS_DIR` (по умолчанию `../models`): `meno-lite-0.1`, `meno-lite-0.2`, `bge-m3`, `bge-reranker-v2-m3`. Допустимы симлинки на уже существующие каталоги и HF snapshots; большие файлы не копируются ради изменения имени. Скрипт проверяет все шарды и токенизаторы Meno. Для каждого запуска сохраняются реальные пути, SHA-256 config/index и размеры/mtime шардов. Это идентификация операторских весов, а не заявление о подтверждённой ревизии их содержимого.

У BGE-M3 основными весами может быть `pytorch_model.bin`. Фильтр скачивания только `*.safetensors` оставит один токенизатор и конфиги: такой каталог не готов для vLLM. Перед `ready` проверьте реальные `.bin`/`.safetensors` и все шарды, перечисленные в index JSON. Проверка pooling-весов также включена в launcher; исходный pinned запуск дополнительно защищён отдельным asset gate на headnode.

Обязательные переменные из инструкции кластера заданы в sbatch: `PIP_CACHE_DIR`, `PYTORCH_CUDA_ALLOC_CONF`, `HF_HOME`, `DO_NOT_TRACK=1`, `HF_DATASETS_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `ANONYMIZED_TELEMETRY=False`, `OUTLINES_CACHE_DIR`, `TORCH_HOME`, `XDG_CACHE_HOME`, `TRITON_CACHE_DIR`, `FLASHINFER_WORKSPACE_BASE`. Дополнительно включён `HF_HUB_OFFLINE=1`; HTTP-прокси подготовки удаляются из окружения вычислительного задания. У отдельных vLLM executor разные подкаталоги kernel-кэшей.

Launcher добавляет `bin` серверного окружения в `PATH` каждого vLLM-процесса. Это нужно для JIT-сборки FlashInfer: абсолютный путь к `vllm` сам по себе не делает установленный рядом `ninja` доступным. Проверьте `<vllm-env>/bin/ninja --version` до отправки; системное окружение и драйверы менять не требуется.

`FASTEMBED_CACHE_PATH` указывает на перенесённый в node-local scratch каталог `.cache/fastembed`. Он нужен также внутреннему BM25, который RAGU создаёт для гибридного подбора ICL-примеров без явного `cache_dir`. Офлайн-проверка должна включать `BM25(language="russian")` без `cache_dir` при этом окружении: проверка только BM25 основного индекса не покрывает ICL.

Если один benchmark-worker завершился, пока второй продолжает работу, `scripts/recover_ragu_worker.py` позволяет возобновить только остановившуюся модель внутри той же Slurm allocation. Он проверяет отсутствие живого worker, архивирует незакрытые graphs вместе с их answers/retrieval и сохраняет закрытых пользователей. Для случая буквального управляющего символа внутри JSON-строки helper делает только экранирование: равенство декодированных значений проверяется, исходный wire-ответ архивируется и остаётся в `original_wire_text`. Запрос, greedy/seed/repetition penalty, схема, факты и метрики не меняются. Другие повреждения JSON и неполные генерации этим правилом не исправляются; QC остаётся строгим. Исправляется только node-local копия generation cache, исходный durable cache не переписывается. Recovery-аудит нужно сохранять вместе с результатами.

Запускать helper следует через отдельный `srun --jobid=<job> --overlap` с тем же offline-окружением, `PYTHONPATH`, node-local work и серверными cache paths. Обязательные аргументы: `--config <work/config.pair.json> --model <label> --run-folder <work/runs/ragu-.../label> --state <persistent/recovery-status.json> --log-dir <persistent/recovery-logs>`. Параллельный живой worker не архивируется. Старый supervisor продолжит показывать exit code первого процесса: фактический replacement PID/прогресс находятся в recovery-state. Окончательное завершение подтверждается QC обоих наборов и checkpoint, а история первого сбоя сохраняется.

## Запуск

Из корня репозитория на headnode:

```bash
export MODELS_DIR=/absolute/path/to/models
export MENO_PAIR_REVISION=$(git rev-parse HEAD)
sbatch --export=ALL scripts/meno_pair_a800.sbatch
```

Параметры очереди: `a800`, один узел, 32 CPU, вся память узла, exclusive; лимит семь суток, `--requeue`, предупреждающий `SIGUSR1` за пять минут до лимита. Шаблон **не делает бесконечных resubmit** при ошибках приложения. Разрешённый планировщиком requeue после сбоя узла или повторная подача того же скрипта восстанавливают последний совместимый чекпоинт. Для продолжения сохраните прежние commit, веса, окружения и параметры; смена identity создаёт другой эксперимент. При заданном `MENO_PAIR_REVISION` несовпадение HEAD вызывает явную ошибку.

| Назначение | Выделенный GPU, логический индекс | Порт | Контекст |
|---|---:|---:|---:|
| Meno 0.1 native | 0 | 9022 | 32768 |
| Meno 0.1 YaRN ×2 | 1 | 9025 | 65536 |
| Meno 0.2 native | 2 | 9032 | 32768 |
| Meno 0.2 YaRN ×2 | 3 | 9035 | 65536 |
| BGE-M3 | 4 | 9023 | 8192 |
| BGE reranker | 5 | 9024 | 8192 |

Числа GPU — позиции внутри выделенного Slurm набора, не произвольные физические ID. Остальные выделенные карты не используются этим профилем. У каждой Meno две копии одних весов, чтобы **короткие запросы не проходили через YaRN**. Полный бюджет ≤32768 идёт на native; длиннее — на YaRN до 65536. Все API слушают loopback compute node; Mac не участвует в запросах бенчмарка.

У кандидатов одинаковы greedy, seed 42, repetition_penalty 1.03, dtype half, память 0.90 на отдельной карте; native max-num-seqs=16/batched-tokens=16384, long 4/8192. Протокол RAGU/NEREL/BM25+dense/local search/reranker сохранён; runtime concurrency=8 на каждую модель. Сначала готовятся шесть сервисов, затем два независимых RAGU worker запускаются одновременно. Нельзя сравнивать эти времена с пилотами как изолированный тест скорости декодирования.

## Хранилище и чекпоинты

`/userspace` на этом кластере — NFS. Живые Qdrant/SQLite и DiskCache работают **на локальном scratch** узла (`CLUSTER_LOCAL_SCRATCH`, по умолчанию `/tmp/meno-rumba-...`). Сетевой filesystem для live scratch отклоняется. На scratch нужно минимум 15 GiB, в постоянном хранилище минимум 12 GiB перед стартом; это начальные проверки, а не гарантированный верхний предел результата.

Исходники клонируются с локального диска на фиксированный commit, данные и BM25 staging копируются без сетевых запросов. Веса и Python-окружения используются по абсолютным постоянным путям. В `runs/a800-meno-pair/<fingerprint>/` лежит постоянное состояние:

- `identity.json`: код, протокол и идентичность весов; `workflow.lock` предотвращает второй writer того же запуска;
- `jobs/JOB_ID-RESTART/`: команды и PID, allocation, отдельный лог каждого vLLM и двух benchmark workers, пути scratch;
- `status.json`: heartbeat примерно раз в минуту, количество ответов из 1543 на модель, состояние worker и ошибки;
- `statistics/*.json`: сразу после запуска и затем примерно раз в час — прогресс, ошибки/обрезания, GPU memory/utilization/power;
- `checkpoints/latest.json` и `previous.json`: атомарные manifests последних завершённых фиксаций;
- `checkpoints/objects/`: неизменяемые графы завершённых пользователей и их ответы/контексты;
- `checkpoints/cache/`: атомарно сохранённые raw LLM responses и точные token counts, включая генерации незавершённой истории;
- `results/runs/ragu-HASH/`: ответы и пересобранные отчёты, пригодные для последующего запуска судьи.

Чекпоинт выполняется сразу после старта workers, приблизительно каждый час, после завершения каждой модели и перед выходом по `SIGTERM`, `SIGINT` или предупреждению Slurm. Интервалы можно изменить через `CHECKPOINT_SECONDS` и `STATISTICS_SECONDS` (по умолчанию 3600). Данные графа разрешено копировать только после `graph.index.close()` и успешного QC всех ответов этого пользователя. Live базы и частично построенные графы не принимаются за контрольную точку.

Публикация нового `latest.json` происходит только после полного копирования и переименования новых объектов. При ошибке копирования прежний manifest остаётся действующим. Большие графы и raw-cache append-only: очередной checkpoint не дублирует все предыдущие гигабайты. При восстановлении завершённые пользователи и ответы возвращаются на новый локальный scratch; незавершённый пользователь строится заново с переиспользованием сохранённых raw генераций. Часть работы после последней успешной фиксации при гибели узла может потребовать повторения.

**Падение интернета на Mac не прерывает начатый offline-бенчмарк:** его процессы, сбор статистики и чекпоинты работают в Slurm allocation. Во время первоначального скачивания ресурсов Mac-прокси ещё может быть нужен; вычислительная стадия не начнётся до завершения подготовки. Почасовой контроль из чата — дополнительный монитор, а не механизм сохранения данных.

## Первые пять минут и дальнейший контроль

```bash
squeue -u "$USER"
tail -n 100 slurm-meno-pair-JOB_ID.log
cat runs/a800-meno-pair/current.json
# По durable-пути из current.json:
cat runs/a800-meno-pair/FINGERPRINT/status.json
cat runs/a800-meno-pair/FINGERPRINT/checkpoints/latest.json
ls runs/a800-meno-pair/FINGERPRINT/statistics/
```

Проверьте, что bootstrap дошёл до `ready`, сервисы последовательно стали готовы, два worker начали вопросы и появился успешный checkpoint. Если node-local диск, драйвер/CUDA, зависимости или веса не подходят, ошибка остаётся в Slurm/модельном логе; это не считается успешным прогоном. При ошибке одного worker второй может завершить свою колонку, затем общий job сообщает nonzero status. Если перестал работать общий сервис или запись чекпоинта, ошибка также фиксируется и задача останавливается с сохранением предыдущей контрольной точки.

Финальный успех — `phase=complete`, по 1543 уникальных ответа и успешный QC каждой модели, `checkpoints/latest.json` с `final=true`. Отчёты имеют `judge_pending`: F1 уже рассчитан, официальный rumba_metric ждёт отдельного Pollux. Для судьи используйте сохранённый `results/runs/ragu-HASH`, а не потерянный после allocation локальный `/tmp`.
