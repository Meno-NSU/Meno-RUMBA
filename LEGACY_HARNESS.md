# Предыдущий custom harness RUMBA

Этот документ описывает предыдущие эксперименты. Текущий RAGU harness описан в README.md.

Клиент, извлечённая память, гибридный индекс и отчёты находятся здесь. Генерация, векторные представления и судья работают на удалённых OpenAI-совместимых серверах. Репозиторий включает минимальный снимок промптов, NEREL и `HybridIndex` из `llm-training` в `vendor/training`; полный проект обучения для запуска не требуется. Происхождение и контрольные суммы снимка сохранены рядом. Можно указать собственный полный экспорт через `training_source` в конфигурации.

Рабочие адреса серверов задаются в локальном `config.json`, который исключён из Git. В репозитории находится только `config.example.json` с демонстрационными адресами. `preflight` проверяет список моделей и короткий запрос; результат сохраняется локально в `runs/preflight/`.

Предварительная отладка выявила повторы: в первой пробе 5 из 21 генерации обрезались по лимиту. Ограниченный JSON завершил два из тех проблемных фрагментов, но не устранил все смысловые нарушения связей. Оба режима поддерживаются основным конвейером; окончательный выбор основного варианта отложен. Результаты конкретных запусков, данные, исходные ответы и локальная сводка `runs/status.json` хранятся в `runs/` и не входят в Git. Ниже приведены команды для воспроизведения, а для официальной оценки нужен отдельно настроенный Pollux.

## Установка и проверка

Используется Python 3.12. Для установки после клонирования:

```sh
git clone https://github.com/Meno-NSU/Meno-RUMBA.git
cd Meno-RUMBA
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.lock
cp config.example.json config.json
# Укажите рабочие адреса серверов в config.json перед preflight.
.venv/bin/python scripts/fetch_sources.py
.venv/bin/python -m rumba_bench.cli preflight
.venv/bin/python -m pytest -q
```

`fetch_sources.py` получает несколько файлов официального RUMBA с лицензией, без клонирования его окружения. Ревизия RUMBA: `a20471ab5bb9d6d0b3bc8a263495a799868e1a3b`; ревизия данных: `d0480d86d4ef20701d8538dd3d50528ee065ab63`. Они записаны в `vendor/rumba/manifest.json`. Контрольные суммы проверяются при загрузке функций метрики.

## Данные и пилот

```sh
.venv/bin/python -m rumba_bench.cli prepare
.venv/bin/python -m rumba_bench.cli estimate --suite pilot
.venv/bin/python -m rumba_bench.cli estimate --suite full
```

Данные читаются через `datasets.load_dataset("ai-forever/RUMBA", "ru", split="test", streaming=True, revision=...)`. `prepare` сохраняет 1 543 вопроса и 85 историй в `data/`; компактная копия занимает 53 МБ. Данные скачиваются при подготовке и не включаются в Git. Повторяющиеся истории проверяются на идентичность и сохраняются по одному разу. Служебные поля `answer`, `evidence` и категории не передаются в извлечение или генерацию ответа.

Пилот зафиксирован в `data/pilot50.json`: 50 вопросов пользователей `user_44`, `user_61`, `user_65`, зерно 42. Четыре группы temporal × session-scope содержат по 12–13 вопросов. Для отладки используются немногие полные истории пользователей: это сокращает число запросов извлечения. Результат пилота нельзя представлять как репрезентативную оценку всей выборки.

| Объём на одну модель | Пилот | Полная выборка |
|---|---:|---:|
| Вопросы | 50 | 1 543 |
| Сессии | 155 | 4 031 |
| Запросы извлечения | 411 | 10 766 |
| Запросы генерации ответа | 50 | 1 543 |
| Запросы судье | 50 | 1 543 |

Общие сессии обрабатываются один раз для данной модели. Между моделями извлечение выполняется независимо: сравнивается качество всего конвейера каждой модели.

## Зафиксированный протокол

### Два режима извлечения

Оба режима реализованы и доступны через `protocol.extraction_decoding` в `config.json` либо параметр `--extraction-decoding free|structured`. По умолчанию используется `free`; это не рекомендация по качеству. Выбор основного режима и возможная доработка остаются открытыми.

- `free`: свободная генерация JSON по промпту; обрезанный или неразбираемый результат сохраняется как ошибка извлечения.
- `structured`: тот же промпт и greedy, но в запрос vLLM добавляется `structured_outputs.json` с типами NEREL и конечными ограничениями. По умолчанию не более 16 сущностей и 16 связей, имя до 80, описание до 200 символов. Лимиты настраиваются через `protocol.structured_limits`. Они могут ограничить полноту памяти и не гарантируют правильности фактов и связей.

```sh
.venv/bin/python -m rumba_bench.cli smoke --extraction-decoding free
.venv/bin/python -m rumba_bench.cli smoke --extraction-decoding structured

.venv/bin/python -m rumba_bench.cli extract --suite pilot --extraction-decoding free
.venv/bin/python -m rumba_bench.cli extract --suite pilot --extraction-decoding structured
```

При использовании параметра командной строки повторяйте его на каждом этапе: `extract`, `retrieve`, `answer`, `score`, `report`. Для отдельного эксперимента по всем трём моделям режим и лимиты должны совпадать. Кэши и результаты имеют префиксы `free-<hash>` и `structured-<hash>`; переключение режима либо изменение лимитов создаёт отдельный протокол и не переиспользует чужую память. Пилот требуется отдельно для каждого режима. Диагностический `scripts/probe_structured.py` по-прежнему доступен для проверки старых проблемных фрагментов и не подмешивает пробы в зачётные результаты.

Параметры в `config.json`: greedy (`temperature=0`), зерно 42, одинаковые промпты и лимиты для трёх моделей. Клиент явно задаёт `top_p=1`, `top_k=-1`, `min_p=0`, `repetition_penalty=1`, `presence_penalty=frequency_penalty=0`, чтобы не зависеть от различающихся настроек генерации в контрольных точках. Используется `one_stage`, компактный `variant=1` из `llm_training/extraction/prompts.py`, полная онтология NEREL с сигнатурами. Сессии идут в хронологическом порядке, тексты режутся на фрагменты до 3 500 символов с перекрытием 200 символов; одновременно обрабатываются два запроса. Выход извлечения — до 4 096 токенов, ответа — до 256, остановка ответа по переводу строки соответствует официальной задаче.

Предварительная отладка: полный промпт `variant=0` на первой сессии зациклился и достиг 4 096 токенов; компактный вариант на ней завершился за 3,6 секунды и 576 токенов. Это техническая проба, не результат бенчмарка. Исходные ответы обоих вариантов сохранены в `runs/smoke/requests/`. Компактный вариант выбран до пилота и должен применяться ко всем трём моделям. Качество компактного варианта на всём пилоте ещё проверяется.

Из JSON извлечения берутся сущности и связи с описаниями и датами. Неизвестные типы, отсутствующие концы связей и нарушения DOMAIN→RANGE записываются в `violations` и исключаются из памяти. Неполный или неразбираемый JSON записывается как ошибка извлечения; исходный ответ сохраняется. Исходные беседы не подмешиваются в контекст ответа. Нормализация и объединение графа отдельной моделью не выполняются.

Документы индекса — отдельные извлечённые сущности и связи. Поиск использует исходный `HybridIndex`: BM25 со стеммингом + нормализованные плотные векторы, RRF с равными весами, `candidate_pool=100`, `top_k=20`. Пользователи имеют отдельные индексы. Даты сессий и дата вопроса входят в контекст. Используются все предоставленные сессии, как в официальном RUMBA RAG; дата вопроса служит временной опорой, автоматический отсев сессий по ней не добавлен. Промпт ответа — официальный `ANSWER_PROMPT_RU`. Лимит контекста 24 000 символов; пропущенные по лимиту документы отмечаются в диагностике.

## Поэтапный запуск на одной GPU

Можно запускать генератор, векторизатор и судью по очереди. После этапа извлечения модель не нужна для построения индекса; после этапа поиска сервер векторов не нужен для генерации ответов. Для каждой команды ниже доступны `--model` и `--suite pilot|full`.

1. Пока работает Meno-Lite-0.2, извлечь память:

```sh
.venv/bin/python -m rumba_bench.cli extract --model meno-lite-0.2 --suite pilot
```

2. Поднять сервер векторных представлений и заполнить `embedding.base_url` в `config.json`. Используется BGE-M3, имя на сервере — `bge-m3`, источник — `BAAI/bge-m3`. Префиксы запроса и документа пустые. Поле `revision` должно отражать реальную ревизию весов; если она неизвестна, оставить `null`, не подставляя ревизию другой модели. Все три колонки должны использовать один и тот же векторизатор.

```json
{
  "backend": "openai",
  "base_url": "http://localhost:8001/v1",
  "model": "bge-m3",
  "source_model": "BAAI/bge-m3",
  "revision": null,
  "batch_size": 16,
  "query_prefix": "",
  "passage_prefix": ""
}
```

Проверить `/v1/models` и `/v1/embeddings`. Если сервер использует другое имя `--served-model-name`, записать его в `embedding.model`. Затем построить индекс и сохранить контексты всех вопросов:

```sh
.venv/bin/python -m rumba_bench.cli retrieve --model meno-lite-0.2 --suite pilot
```

3. Вернуть сервер Meno-Lite-0.2 и получить ответы:

```sh
.venv/bin/python -m rumba_bench.cli answer --model meno-lite-0.2 --suite pilot
```

4. Поднять `ai-forever/pollux-judge-32b` и заполнить `judge`:

```json
{
  "base_url": "http://localhost:8002/v1",
  "model": "pollux-judge-32b",
  "source_model": "ai-forever/pollux-judge-32b"
}
```

```sh
.venv/bin/python -m rumba_bench.cli score --model meno-lite-0.2 --suite pilot
```

Поле `model` — фактическое имя из `/v1/models`, `source_model` — идентичность судьи. При необходимости доступа через ключ добавить `api_key_env` с именем переменной окружения; сам ключ хранится в окружении, не в конфигурации. Клиент не использует системные HTTP-прокси для запросов к указанным серверам.

Если генератор и векторизатор доступны одновременно, `run` последовательно выполняет `extract`, `retrieve`, `answer`. Оценка судьи всегда отдельная:

```sh
.venv/bin/python -m rumba_bench.cli run --suite pilot
.venv/bin/python -m rumba_bench.cli score --suite pilot
```

После отладки пилота те же команды запускаются с `--suite full`; общие извлечения переиспользуются. Полный объём блокируется, пока под тем же протоколом не получены 50 ответов без ошибок извлечения. Если пилот выявил обрезанный или неразбираемый JSON, сначала изучить исходные ответы и исправить общий протокол, затем повторить пилот. Ошибки нельзя скрывать пересчётом только удачных примеров.

Для следующих моделей заполнить соответствующие объекты в `models`: `meno-lite-0.1` и `qwen2.5-7b-instruct`. Указать URL, фактическое имя модели и описание ревизии весов. Те же команды запускаются с `--model meno-lite-0.1` или `--model qwen2.5-7b-instruct`. При последовательной замене весов по одному адресу достаточно дождаться готовности `/v1/models`; скрипт проверяет ожидаемое имя модели.

## Метрики и результаты

### Калибровка параметров для релиза

Параметры `protocol.repetition_penalty` и `protocol.top_p` задаются явно в каждом запросе, входят в хеш протокола и применяются одинаково ко всем сравниваемым моделям. Зачётный бенчмарк сохраняет `temperature=0`, зерно 42. Изменение штрафа создаёт новый протокол и требует нового пилота. Настройки релиза исследуются отдельно; они не меняют уже запущенный зачётный прогон.

```sh
.venv/bin/python scripts/tune_decoding.py
```

Скрипт отдельно сравнивает штрафы `1.0, 1.03, 1.05, 1.10, 1.15` при нулевой температуре на девяти синтетических примерах из `fixtures/decoding_dev.json` и, если они есть локально, пяти зациклившихся и трёх успешных технических фрагментах. Затем проверяет температуры `0.2` и `0.5` при выбранном штрафе на синтетических примерах с зёрнами 42 и 43. Зачётные ответы RUMBA и их F1 для выбора настроек не используются. Пробы на прошлых сбоях оценивают техническое завершение и формат извлечения.

Измеряются завершение ответа, корректность JSON, повторы артефактов, нарушения онтологии, полнота заранее указанных сущностей и выполнение коротких заданий. В заданиях есть обязательные повторы слов и чисел: штраф не должен запрещать нужное повторение. Кандидат должен сохранить качество синтетических ответов относительно исходной настройки, после чего выбирается по техническим сбоям, полноте и повторам. Это предварительная калибровка одной модели, а не доказательство глобально оптимальных параметров или семантической корректности.

Сводка и строки оценивания сохраняются в `runs/decoding-calibration/<hash>/`, а исходные ответы переиспользуются из общего кэша `runs/decoding-calibration/requests/`. Переоценка тех же ответов другим кодом не требует новых запросов к GPU. Скрипт формирует `generation_config.greedy.patch.json` и отдельный `generation_config.sampling.patch.json` для необязательного режима с выборкой токенов. Это предложения для слияния с существующим `generation_config.json`; они не заменяют идентификаторы специальных токенов и не изменяют веса или файлы на сервере. Окончательное решение для релиза требует более широких заданий и оценки независимым судьёй.

`rumba_metric` использует точные функции `judge_template`, `process_judge_response`, `extract_judge_feedback` из закреплённого официального RU-модуля. Они загружаются через AST без запуска тяжёлого конструктора LightEval, который загружает Pollux локально. Вместо него тот же промпт отправляется удалённому Pollux. Оценки 0/1 дают 0; оценки 2/3 дают 1. Неразбираемый вердикт даёт 0, как у авторов, и отдельно учитывается в `judge_parse_errors`. Дата добавляется к вопросу в точности по официальной функции. Замена Pollux другой моделью не выдаётся за официальный RU-результат.

F1 повторяет `Metrics.f1_score` LightEval 0.13.0, используемой окружением RUMBA: множества слов после `split()`, без приведения регистра, удаления пунктуации, стемминга или учёта повторов. Семантика проверяется тестом непосредственно против метода из исходника LightEval. Это отличается от часто используемого нормализованного токенного F1.

Результаты сохраняются в `runs/<mode>-<protocol-hash>/<model>/`:

- `retrieval/pilot/*.json` — готовые контексты и диагностика поиска;
- `answers/pilot/*.json` — ответы, эталоны, категории, время и токены;
- `scores/pilot/*.json` — оценки Pollux и пояснения;
- `pilot/report.json`, `pilot/predictions.json`, `pilot/qc.json` — сводка и состояние пилота;
- `requests/`, `judge-requests/` — исходные запросы и ответы.

В родительской папке: `comparison-pilot.md`, `comparison-pilot.csv`, затем аналоги для `full`. Таблицы содержат все три колонки моделей, общий результат и temporal × session-scope. Неизмеренные колонки явно помечаются как ожидающиеся. Дополнительно считаются полнота поиска сессий `evidence`, доля вопросов со всеми найденными сессиями, ошибки JSON и нарушения онтологии. `evidence` применяется только для этой диагностики.

Извлечения хранятся отдельно в `runs/extraction/<mode>-<extraction-hash>/<model>/`, поэтому добавление адреса векторизатора или судьи не требует повторять извлечение. Полный и пилотный этапы одного режима используют общие сохранённые извлечения. Изменение промптов, данных, кода конвейера, параметров извлечения или модели создаёт другое пространство результатов. Для пересоздания отчётов без запросов к GPU:

```sh
.venv/bin/python -m rumba_bench.cli report --suite pilot
```

## Расходы на локальную машину

На момент подготовки: `.venv` около 296 МБ, данные 53 МБ, веса LLM и векторизатора локально отсутствуют. Тяжёлые библиотеки обучения, PyTorch и CUDA не устанавливаются. Нагрузка клиента — HTTP, BM25 и небольшие операции NumPy; размер памяти зависит от числа извлечённых сущностей. Исходные запросы и ответы полного прогона могут занять сотни мегабайт или несколько гигабайт на три модели. Основные вычислительные расходы приходятся на удалённое извлечение. `estimate` показывает точное число запросов, а не обещанное время исполнения.

Источники: [RUMBA](https://github.com/ai-forever/RUMBA), [данные](https://huggingface.co/datasets/ai-forever/RUMBA), [LightEval 0.13.0](https://github.com/huggingface/lighteval/blob/v0.13.0/src/lighteval/metrics/metrics_sample.py). Лицензии исходных фрагментов находятся в `vendor/`.
